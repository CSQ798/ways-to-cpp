04

迷宫最短路径

像水波一样，一圈一圈地扩散

难度 ★★★☆☆ 建议 5–7 小时 主线：广度优先搜索 阶段二

本板块会用到的新知识点

从这里开始，你正式进入「算法」。好消息是：这个算法只有二十行。

  • std::queue 队列　需要 #include <queue>。 「先进先出」的容器。用 push() 从队尾放进，用 front() 看队首、pop() 弹出队首。 它和栈（后进先出）的区别，就是「一圈一圈扩散」和「一条路走到黑」的区别。
  • std::pair　需要 #include <utility>。 把两个值捆成一件东西，比如一个坐标 Cell(3, 5)。 它可以直接用 == 比较，所以写 if (cur == goal) 就够了。
  • 广度优先搜索（BFS）　这是思想，不是语法：把起点放进队列，每次取出一个，把它的所有「下一步」放到队尾。 因为队列是先进先出的，所以所有距离为 1 的格子会先被处理完，才轮到距离为 2 的。 于是——第一次到达终点时走的路，一定是最短的。
  • visited / dist 表　形如 std::vector<std::vector<int>> dist。 一张和地图同样大的表，记录「到每个格子最少要几步」。它顺便还兼任了「来没来过」的标记。
  • 前驱表与路径回溯　代码里的 parent。 BFS 只告诉你「最短是 128 步」，不告诉你「怎么走」。于是我们顺手记下「我是从哪个格子来的」， 最后从终点一路倒推回起点，路就出来了。

一、这件事在真实世界里长什么样

你手机里的导航软件规划的路线、游戏里 NPC 找到你的路径、社交网络里「你和某个人隔了几度」、 网络数据包经过了几台路由器——这些问题的数学形式完全一样：一张图，从一点到另一点，最少几步。

解决办法朴素得让人意外：从起点开始一圈一圈往外扩散，扩散到终点为止。 这不就是往平静的水面丢一颗石子吗？最先漫到岸边的那个水波，走的一定是最直的路线。

二、任务拆解：三关

  1. 把地图读进来，把规则写清楚

    用 std::vector<std::string> 存地图（# 是墙，. 是路）。 写一个打印函数，再写一个「这个格子能不能走」的判断。这一关只是把问题描述清楚，还没开始搜索。

  2. 算出最短步数

    建一个和地图等大的 dist 表，全部填 -1 表示「没去过」。 起点入队、距离记 0，然后开始循环：取出队首，把四个方向上「能走且没去过」的邻格记上「当前距离 + 1」并入队。 能打印出 128 这个数字，这一关就过了。

  3. 把路画出来

    再加一张 parent 表，入队时顺便记下「我是从哪来的」。 搜索结束后，从终点一路顺着 parent 往回走，把沿途的 . 改成 *。

  1. 「最短」这个要求，被策略本身免费满足了。 代码里没有任何一行在比较「哪条路更短」。 它只是在扩散。扩散的顺序天然保证了先到的一定最短。这就是算法的美：不是算得更快，而是想得更对。
  2. 一张表干了两件事。 dist[r][c] 是 -1， 既表示「没访问过」，也表示「到不了」。一个哨兵值同时承担两种含义，于是 if (dist[nr][nc] != -1) continue; 这一行就同时挡住了「重复访问」和「绕圈」。
  3. 「算距离」和「还原路径」是分开的。 BFS 只负责填 dist， 回溯只负责读 parent。两段逻辑互不干扰，各自都能单独看懂。把「求解」和「呈现」分开，是工程上极重要的一刀。
  4. 方向数组思想在项目 03 出现过，这里又出现了。 四个方向写成 DR/DC 两张表， 于是「上、下、左、右」变成一次循环。好思想会被反复用到——这正是它们值得被记住的原因。
  5. 传引用还是传 const 引用，取决于你要不要改它。 shortestPath(Grid& grid, ...) 用的是普通引用，因为它要在地图上画 *； 而 printGrid(const Grid& g) 用 const，因为它只看不改。两个函数签名放在一起，就把意图说完了。
常见陷阱
  • 标记「已访问」必须在入队时，不能等到出队时。 如果在出队时才标记，同一个格子会被好几个邻居重复入队， 队列会膨胀几倍，代码依然能跑对，但慢得莫名其妙。这是个很隐蔽的坑。
  • queue 取队首用 front()，不是 back()。 用错就变成了深度优先——结果不再是「一圈一圈」，最短性立刻失效。
  • pop() 的返回值是 void，它只负责扔掉。 想取值必须先 front() 再 pop()。
  • 网格的行是 std::string，所以 grid[r][c] 取出来的是 char，比较时要用 '#' 而不是 "#"。
  • 起点就等于终点、或者终点被墙包死——这两种情况都要能优雅处理，而不是崩溃。
进阶挑战
  • 把所有最短路径全部打印出来。你会发现从「记录一个父亲」变成「记录所有父亲」，再改成深度优先输出。
  • 允许斜着走（八个方向）。最短步数会变吗？如果斜走一步和直走一步「代价」不一样呢？
  • 给每个格子加上不同的通行代价（草地慢、大路快），这时 BFS 就不够用了，你需要 Dijkstra 算法—— 它和 BFS 只差一个数据结构：把队列换成优先队列。
  • 再加一个「离终点还有多远」的估计值，优先搜索离终点近的方向，这就是 A* 算法，游戏工业里的寻路基石。
05

表达式求值器

用函数的调用层次，表达运算的优先级

难度 ★★★☆☆ 建议 5–8 小时 主线：递归下降分析 阶段二

本板块会用到的新知识点

你会第一次遇到「递归不只是算阶乘」这件事。这个项目的代码量比前几个都少，但思想密度最高。

  • 递归下降分析　这是本项目的灵魂。核心想法只有一句：用函数的调用层次来表达运算的优先级。 加法函数会去调用乘法函数，所以乘法天生就比加法先算——优先级不再是一张需要查的表，而是程序的形状本身。
  • 函数前置声明　形如在文件上方写 double parseTerm(const std::string&, size_t&); C++ 要求「先声明后使用」。而这三个函数互相调用，谁也无法排在第一个，所以必须先声明、后定义。
  • 引用参数共享状态　size_t& pos 三个函数需要共享同一个「读到哪了」的光标。用引用而不是全局变量，既不破坏封装，也不需要写一个类。
  • std::atof　需要 #include <cstdlib>。 把一段字符串转成 double。有了它，我们不必手写「数位乘十累加」。
  • size_t　无符号整数类型，专门用来表示「长度」和「下标」。标准库容器的下标就是它。

一、这件事在真实世界里长什么样

你在计算器里敲下 1 + 2 * 3，它回给你 7。为什么不是 9？因为你默认了乘号先算。 可计算机只会从左往右读字符，它凭什么知道该先算哪一段？

这个问题是编译器技术的起点。JavaScript 引擎要理解你的代码、Excel 要计算公式、SQL 要解析查询语句， 走的都是同一条路：先把表达式理解成一棵树，再算这棵树。

而写这棵树最短的写法，叫递归下降——三十行代码，三个函数，就能把一个完整的四则运算表达式吃透。

二、任务拆解：三关

  1. 只会加法

    写一个函数，只处理「数字 + 数字 + 数字」这种形式。先跑通「读一个数字」和「吃掉一个加号」这两件事， 不要贪多。这一步的目的是想清楚「光标 pos 是共享的」。

  2. 加入乘除，让优先级自然出现

    把原来的函数拆成两个：一个只管加减，一个只管乘除。让「加减函数」在需要操作数时去调用「乘除函数」。 体会一下：你一行优先级判断都没写，但 1 + 2 * 3 已经等于 7 了。

  3. 加入括号和负号

    再加最里层的第三个函数：它负责「读一个数字」「处理括号」「处理负号」。 遇到左括号时，它递归调用最外层的加减函数——于是括号里的世界重新开始，任何复杂度都被这一行递归抹平了。

  1. 优先级变成了结构，而不是规则。 传统写法要先做「中缀转后缀」，还要维护一个运算符栈、 查一张优先级表。而这里，优先级就是「谁调用谁」：加减在顶层、乘除在中间、括号和数字在最里面。 越靠里，越先被算出来。代码的层次结构，直接对应了数学的结构。
  2. 一个引用参数替代了一个类。 三个函数共享 size_t& pos， 没有全局变量、没有对象、没有成员函数。对于这么小的一个问题，这是最轻的表达方式。 「够用就好」本身就是一种优雅。
  3. 三个函数，每个都短到一屏能看完。 而且它们的名字就是它们的职责：parseExpression 管整个表达式， parseTerm 管一个项，parseFactor 管一个因子。 能一句话说清的函数，才配拥有一个好名字。
  4. 递归在这里不是炫技，而是唯一的自然写法。 括号可以套括号，套多少层事先并不知道—— 这正好是递归天生要解决的问题。
  5. 「吃掉一个字符」这个动作被写得非常明确。 const char op = s[pos]; ++pos; 先把记下来，再前进。把「读」和「移动」分开写，能避免绝大多数「少读一个字符」的 bug。
常见陷阱
  • 忘记 ++pos 会导致死循环。 函数不再前进，while 就永远转下去。 第一次写的时候几乎一定会遇到，遇到之后你会永远记住它。
  • 括号不匹配时，这个简版实现会安静地返回一个错误结果，而不是报错。 「出错时大声说出来」是工程代码的基本原则——这里留给你在进阶挑战里补上。
  • 三个函数互相调用，前置声明一个都不能少，而且声明和定义的签名必须完全一致，否则链接时会报「未定义」。
  • 这里全程用 double，所以 10 / 4 得到 2.5。 如果换成 int，得到的就是 2——整数除法截断是初学者永恒的坑。
进阶挑战
  • 加上乘方 ^。注意它是右结合的：2^3^2 应该是 2^9 = 512 而不是 8^2 = 64。 你会发现自己需要把某个 while 改成递归调用。
  • 支持变量 x，并用项目 02 学过的 map<std::string,double> 存变量表。 做完这一步，你手里就有了一个「公式引擎」——Excel 的一小部分。
  • 加入函数调用：sin(0)、max(3, 5)。你需要处理逗号分隔的多个参数。
  • 把「解析」和「计算」彻底分开：先解析成一棵树（结构体 + 指针就是天然的树），再写一个 evaluate 去遍历它。 这一步做完，你就摸到了编译器的门。
06

井字棋与极小极大

写一个你永远赢不了的对手

难度 ★★★★☆ 建议 6–9 小时 主线：对抗性搜索 阶段二

本板块会用到的新知识点

这是第二阶段的高潮。递归在这里第一次用来「思考」，而不只是用来「遍历」。

  • 极小极大搜索（Minimax）　思想：我走一步时，假设我选最好的；对手走一步时，假设他选对我最坏的。 递归下去，每个局面都会得到一个分数，我选分数最高的那一手。这套逻辑适用于一切「有对手」的场景，也是早期国际象棋程序的基础。
  • 按值传参　形如 int minimax(std::vector<char> board, ...)，注意 board 前面没有 &。 每次递归都拿到棋盘的一份独立副本。于是「试走一步」和「撤销这一步」变成了天然的动作—— 函数返回时副本自动消失，外面的棋盘毫发无损。这是用一点点拷贝开销买来的、极干净的一段递归。
  • std::numeric_limits　需要 #include <limits>。 std::numeric_limits<int>::min() 就是 int 能表示的最小值。 求最大值时把初值设为它，比硬编码一个 -999999 更安全、也更说明意图。
  • std::min / std::max　需要 #include <algorithm>。 极小极大的核心操作就是取最小或取最大，标准库直接给你了。
  • 递归中的「试—评—撤」模式　这是回溯算法的通用骨架，八皇后、数独、全排列，用的都是它。

一、这件事在真实世界里长什么样

井字棋只有九个格子，规则简单到小孩都会玩。但正因为简单，它成了「机器如何做决策」最好的教具： 它小到可以穷举所有未来，又大到不能一眼看穿。

一九五零年代，程序第一次在井字棋上做到了不败。从那里出发，加上更聪明的剪枝、更准确的局面评估， 才有了后来的跳棋程序、国际象棋的深蓝，直到 AlphaGo。你接下来写下的这二十行递归，是那整条路的起点。

二、任务拆解：三关

  1. 先把规则写清楚

    用 std::vector<char> 表示九宫格。写三个函数：打印棋盘、 判断谁赢了（八条连线，用一张表存起来）、判断是否下满。这一关没有递归，全是基本功。

  2. 做一个「随便下」的对手

    写一个函数，在所有空位里随便挑一个落子。先让它能陪你下完一整局—— 你会立刻发现：随便下的 AI 输得很难看。这个落差，就是第三关的动力。

  3. 把「随便」换成「算尽」

    写 minimax(board, player, depth)： 如果已经分出胜负，返回一个带深度的分数；否则轮到谁走，就把每个空位都试一遍，递归拿到分数， 我方取最大、对方取最小。最后用 bestMove 在根节点挑出最好的那一手。

这段代码美在哪里
  1. board 按值传递，是整个设计里最漂亮的一手。 因为传的是副本，函数里可以放心地 board[i] = player; 试走一步， 递归返回之后什么都不用管——「撤销」这个动作被语言的机制免费完成了。 如果传的是引用，你就必须记得在每一层手动撤回，多一条 return 路径就是多一个 bug。
  2. 分数设计藏着一个精妙的心思。 10 - depth 和 depth - 10： 赢要赢得快，输要输得晚。因为「输得晚」意味着对手还得再想几步，也就意味着中间还有翻盘的机会。 两个减号，就把「效率」这个额外目标写进了评价体系。
  3. 统一用一套搜索处理双方。 同一个 minimax 既能当 AI 的大脑，也能当「模拟对手」的大脑， 只需要换一个 player 参数。没有写两份对称的代码——这是抽象的胜利。
  4. 「选」与「评」分离。 minimax 只回答「这个局面值多少分」， bestMove 只回答「那我该走哪一步」。两个问题分开问，两个函数分开写， 于是 minimax 可以被原封不动地复用到别的地方。
  5. 用 numeric_limits 而不是魔法数字。 std::numeric_limits<int>::min() 一眼就说明「我要一个尽可能小的起点」， 而 -99999 只会让读者停下来猜：为什么是九万九千九百九十九？
常见陷阱
  • 判断输赢和判断下满的顺序不能反。 必须先看有没有人赢，再看是不是满了。 否则最后一步落子成五的情况会被判成平局。
  • 如果改成按引用传递，每一条 return 之前都必须撤销试走的那一步。 漏掉任何一条，棋盘就会带着「幽灵棋子」继续往下算。这是回溯算法最经典的 bug。
  • 极小极大的代价是「分支数的深度次方」。井字棋最多 9! ≈ 36 万种局面，秒出结果； 但换成五子棋（15×15），同一段代码会把你的电脑算到天荒地老。算法正确，不等于算法可用。
  • 递归太深会撑爆调用栈。井字棋最多 9 层，绝对安全； 但如果你把棋盘改成 20×20，程序会以「栈溢出」的方式崩溃，而不是算得慢。
进阶挑战
  • 加入 alpha-beta 剪枝：如果已经知道某条分支不可能更好，就根本不用搜它。 在井字棋上，它能把搜索量减少到十分之一左右，而结果一模一样。这是本手册里性价比最高的一个优化。
  • 加一个计数器，统计搜索了多少个局面，对比剪枝前后的数字。你会对「优化」这个词有实感。
  • 用 map 把「局面 → 分数」缓存下来，避免重复计算同一个局面（这就是记忆化搜索）。 你会看到搜索次数骤降，而结果一丝不差。
  • 把它变成一个可以真正对弈的程序：用 cin 读入玩家落子，先让你自己输几局。
  • 推广到四子棋（Connect Four）的 7×6 棋盘。你需要加上「只往前看 N 层」的限制和一个粗略的局面评估函数—— 恭喜，你已经摸到了现代博弈程序的核心思路。
